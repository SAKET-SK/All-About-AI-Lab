## Tools as the Action Space

**In plain terms:** a tool schema is one item on a menu the model reads.
It has a `name` (what the item is called), a `description` (the
waiter's explanation of what it does and when to order it), and an
`input_schema` (what details you need to give when ordering). The model
can only pick from what's on the menu — if a tool isn't registered, that
action doesn't exist for it, no matter how smart the model is.

- The model's action space is *exactly* the set of registered tool
  schemas. Add a tool, add an action; remove one, remove the action.
- `description` is the **only at-runtime channel** for telling the model
  when to call a tool — treat it as documentation written for the model,
  not for a human reader. A vague description leads to a misused tool,
  not because the model is careless, but because that's genuinely all
  the guidance it was given.
- `required` is a hard contract enforced by the API before the
  dispatcher ever sees the call.
- Categorical fields (`claim_type`, `severity`) use `enum` so the model
  cannot invent a value outside the allowed set.

**The four tools implemented:**

| Tool | Purpose |
|---|---|
| `lookup_policy` | Fact-gathering — confirms a policy exists, returns coverage/deductible/status/holder |
| `check_claim_history` | Fact-gathering — prior claim count and most recent claim date |
| `classify_claim` | Classification — commits the model's `claim_type` decision (enum-constrained) |
| `assess_severity` | Classification — commits the model's `severity` decision (enum-constrained) |

## Graceful Tool Failure

**In plain terms:** imagine a waiter goes to the kitchen and the
ingredient is out of stock. One waiter panics, drops the tray, and runs
out — the customer never learns what happened and the whole meal is
ruined. A raised exception is that waiter: it crashes the entire loop
and the model never even finds out something went wrong.

The other waiter calmly comes back and says "we're out of that — want
something else, or should I check with the chef?" That's Graceful Tool
Failure: the error comes back as *data*, not a crash, so the model reads
it on its next turn exactly like any other result and can decide what
to do next.

**The core distinction:** a dispatcher that raises crashes the loop —
the model never sees what went wrong. A dispatcher that returns
`{"is_error": true, ...}` lets the model read the failure on its next
turn and adapt (retry if `is_retryable`, otherwise ask a clarifying
question or escalate).

```python
{
  "is_error": true,
  "error_category": "permanent",
  "is_retryable": false,
  "message": "policy_id 'POL-MISSING' not found"
}
```

Implemented in two layers:
1. **Handler-level** — each tool handler anticipates its own failure
   modes (missing field, policy not found, invalid category) and
   returns `tool_error(...)` directly.
2. **Dispatcher-level safety net** — `dispatch_tool()` wraps every
   handler call in `try/except`, so even an unanticipated bug in a
   handler still surfaces as a graceful error instead of propagating
   into the loop.

## The AST Anti-Pattern Audit

**In plain terms:** a unit test is like a taste test — it runs one dish
through and checks "did this come out right?" That only tells you about
the one meal you tasted. The AST audit is more like a building
inspector reading blueprints: it doesn't care whether tonight's dinner
tasted fine, it checks whether the *kitchen itself* is built to code —
functioning fire exits, wiring done right. It reads the loop's source
code as text/structure (never runs it) and checks for four specific bad
patterns:

1. **Checking for a magic word in the text** — like deciding "the meal
   is done" by listening for the word "done" somewhere, instead of just
   checking whether the plate is empty (the real signal: `stop_reason`).
2. **A special hardcoded rule for one specific tool by name** — like the
   kitchen having a secret rule only for one dish, instead of treating
   every order the same way.
3. **Using a turn counter to force a stop** — like closing the kitchen
   after exactly 5 orders no matter what, instead of asking "is everyone
   actually done eating?"
4. **Peeking inside one order's details to make kitchen-wide decisions**
   — like changing the whole restaurant's layout because one customer
   ordered something spicy.

Unit tests check runtime *behavior*. The AST audit checks
**structure** — it catches decision logic leaking into `loop.py` even
if a passing test suite would never notice, because the bad code could
coincidentally still produce correct output on your current fixtures
while being architecturally wrong. That matters because a test only
proves *today's* code works — six months from now someone could quietly
reintroduce one of these patterns while "just fixing a bug," and the
tests might still pass by coincidence. The audit catches it anyway,
because it's checking the shape of the code, not just today's examples.

| # | Anti-Pattern | Example of what's caught |
|---|---|---|
| 1 | String-membership test against text | `if "done" in response.text:` |
| 2 | Hardcoded branching on tool name | `if block.name == "escalate":` |
| 3 | Turn-count used as a termination decision | `if turn >= 5: return` |
| 4 | Branching on raw tool payload contents | `if tool_input["claim_type"] == "theft":` |

Each audit: `ast.parse` the loop's source (via
`inspect.getsource(run_agent_loop)`), `ast.walk` it, look for the
specific AST shape representing the anti-pattern, and fail if any
instance is found.

**Verified two ways, not just one:**
- `test_clean_loop_passes_all_four_audits` — the real, unmodified loop
  produces zero offenders on every audit.
- Four **positive-control tests** (`test_audit_catches_*_regression`)
  run the same audit functions against deliberately bad snippets, to
  prove each audit actually *would* catch a real regression — not just
  that the current clean code happens to pass.

## How It All Fits Together (Plain Terms)

Picture the whole system as a restaurant one more time:

- The **menu** (tool schemas) defines everything the model is allowed
  to do.
- **Graceful Tool Failure** makes sure that when something goes wrong in
  the kitchen, the customer (the model) hears about it calmly instead of
  the whole restaurant catching fire.
- **The AST audit** makes sure nobody quietly rewires the kitchen to
  break the rules that keep the whole system predictable.

None of these three things talk to each other directly — but together,
they're what makes it safe to let the model run the show turn after
turn without a human standing over its shoulder the whole time.

## Key Takeaway

Two independent safety mechanisms, doing different jobs:
- **Graceful Tool Failure** keeps runtime errors *inside* the
  conversation, where the model can react to them.
- **The AST audit** keeps decision logic *outside* the loop's Python
  branches, where it can't silently override the model's own
  stop_reason-driven control flow — and it keeps catching that even
  after later refactors, not just today.

# Lesson 8, Part 1: Build a Claims Intake Agent — stop_reason-Driven Loop

## Overview

This is Exercise 1 of 3 in the claims intake project. It builds and
tests **only the agentic loop** (`loop.py`) — no tools, no claims
domain logic yet. Those come in Exercises 2 and 3. The loop is
deliberately domain-agnostic: the same four-moment cycle drives a
two-tool weather demo just as well as a four-adjuster-queue insurance
triage system.

---

## The Four Moments of Every Turn

1. **Send** — `client.messages.create(...)` with the running message
   history, tool schemas, and system prompt.
2. **Inspect `stop_reason`** — the single field that tells the harness
   what the model wants next: `tool_use` (keep going), `end_turn`
   (return), or anything else (unplanned — raise).
3. **Execute tools** — if `tool_use`, run every `tool_use` block in the
   response and collect results.
4. **Thread results back** — append the assistant's turn, then ONE user
   turn containing ALL `tool_result` blocks, matched by `tool_use_id`.
   Loop.

---

## Key Principles

- **`stop_reason` is the only control-flow signal.** Not message text,
  not a turn counter, not a magic string. Anything else is a parallel,
  unreliable signal competing with the one the API already provides.
- **Unplanned stop_reason values are exceptions, not guesses.**
  `max_tokens`, `pause_turn`, `refusal`, `stop_sequence` all raise
  `UnexpectedStopReason` naming the value — never silently handled.
- **Multiple `tool_use` blocks in one turn → all executed, all results
  threaded back in a single following user turn.** Never one user turn
  per tool result.
- **"The model controls the loop."** The loop's code never changes based
  on what the agent is doing. What varies (which tool, how many times,
  when to stop) lives entirely inside the model's decisions.
- **The trace is the lifecycle artifact.** One `TurnRecord` per turn
  (stop_reason + tool calls made) is enough to reconstruct any run
  after the fact for debugging or auditing.
- **`max_turns` is a harness-level safety net**, independent of the
  model — it stops a runaway loop even if the model "wants" to keep
  going.

## Running the Tests

```bash
pip install pytest

# Verify the reference solution (should be 9 passed):
PYTHONPATH=solution python -m pytest tests/ -v

# Work through the starter's TODOs yourself:
PYTHONPATH=starter python -m pytest tests/ -v
```

No `ANTHROPIC_API_KEY` needed — the `ScriptedClient` in
`tests/scripted_client.py` returns a fixed, pre-built sequence of
responses that mimic the real SDK's shape (`.stop_reason`, `.content`
with `.type`/`.text`/`.id`/`.name`/`.input`), so the loop's control flow
is tested deterministically and for free.

**Verified:** solution passes all 9 tests; starter fails with
`NotImplementedError` until the TODOs are filled in (confirmed both
ways before shipping this).

## Key Takeaway

The loop itself is intentionally boring and mechanical — three or four
lines to triage `stop_reason`, the same regardless of domain. All the
intelligence (what tool, when, how many times) lives in the model. The
harness's only job here is to be a faithful, well-tested channel for
that decision — which is exactly why this file has zero knowledge of
insurance, claims, or adjusters, and why it's fully testable offline.
